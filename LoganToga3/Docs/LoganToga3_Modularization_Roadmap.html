0. エグゼクティブサマリー

推奨方針: 「責務分離 → 契約テスト → ソース境界 → 静的ライブラリ → 必要な箇所だけDLL → 差分チェック」の順で進める。DLL化は最終目的ではなく、安定した境界が実証されたモジュールにだけ適用する。

後から境界化する

振る舞いとデータ所有権が安定し、契約テストが揃ってから扱う。

当面は統合層に残す

変更頻度とSiv3D依存が高い領域は、無理にABI境界へ固定しない。

期待効果: 変更されていない内部実装の再読を減らし、通常確認を「変更モジュール、直接依存先、公開契約、統合スモークテスト」へ絞る。電力・水資源の削減量は計測なしに断定せず、ビルド時間、解析対象ファイル数、テスト時間、キャッシュヒット率を代理指標として測定する。

1. 原則と非目標

設計原則

  1. 証拠による省略: DLLだから省略するのではなく、同一ハッシュ・同一契約・通過済みテストを根拠に内部再確認を省略する。
  2. 一方向依存: 上位層だけが下位層を知り、FoundationやDomainからUI、Scene、Appを参照しない。
  3. 所有権の単純化: 生成したモジュールが破棄する。DLL境界を跨いで任意のヒープオブジェクトを解放しない。
  4. 小さな契約: 巨大な共有状態ではなく、処理に必要なスナップショット・コマンド・結果だけを渡す。
  5. 可逆的移行: 1フェーズ1境界とし、切り戻せる差分サイズを保つ。
  6. 計測して判断: ビルド、テスト、解析の所要時間を前後比較し、効果がない分割は増やさない。

非目標

  • すべてをDLLへ移すこと。
  • 未変更DLLを永久に無監査とすること。
  • 現在の巨大な共有構造体をそのままDLLへ隠すこと。
  • 仕様未確定の将来関数を大量に固定すること。
  • モジュール化と同時にゲーム仕様やUIを大規模変更すること。
  • 測定せずに環境負荷削減量を主張すること。

2. 現状診断

調査時点では LoganToga3.vcxproj が単一の Application プロジェクトであり、Debug/Release x64、Siv3D 0.6.16、/MTd・/MT を使用する。実装の多くはヘッダー内の inline 関数で、プロジェクト登録上は専用テストプロジェクトが確認できない。

領域現状の役割主な結合判断
Main.cpp 引数解釈、Mod読込、定義生成、音楽設定、Scene起動 起動手順と具象サービスを直接呼出し 最終的なComposition Root。DLLにはしない。
App/AppSceneSharedData.h Scene間共有状態 Font、Texture、UI、Mod、定義、音楽を同居 分割対象だが、初期のバイナリ境界にはしない。
App/AppRuntimeState.h 戦闘実行時の統合状態 BattleWorld、定義、描画、音声、通知、Modを束ねる Application Facade導入後に縮小する。
BattleWorld/BattleWorldStores.h データ指向の戦闘状態 Siv3D型、DefinitionStores、音声・Modポインターを保持 Simulation候補。ただし外部資源ポインターを先に排除する。
Systems/PathfindingSystem.h スナップショット生成、A*、座標変換、経路更新 純粋計算とBattleWorld、UI/QuarterView依存が混在 最初の分離パイロットに適する。
Data/ModContent.h ID正規化、安全なパス、倉庫探索、manifest読込 filesystem、Siv3D、TOML、探索方針が混在 Pure PolicyとI/O Adapterへ分ける。
Data/DefinitionLoaders.h 定義ロードと参照整合性検証 具象TOMLローダーとStoreへ直結 検証を純粋化し、読込はAdapterへ残す。
Data/MusicSettingsService.h TOML設定の読書きと安全な置換 Siv3D FilePath/TOML、状態文言 永続化パターンの契約化候補。音楽UIとは分ける。
UI/* / Scenes/* 入力、描画、Editor、Scene制御 Siv3Dと共有状態への強い依存 Host側に残し、Port経由でCoreを利用する。
最重要の構造課題: ディレクトリは既に責務別に見えるが、コンパイル境界と依存規則はまだ弱い。特に PathfindingSystem.h から UI/QuarterView.h を参照するような「Domain/System → UI」の依存を先に解消しなければ、ライブラリ化しても横断調査は減らない。

4. 分離候補と優先順位

順位候補先に行う分離利点主な危険DLL判断

5. API / ABI設計方針

ソース・静的ライブラリ境界

  • 公開 include/ と内部 src/ を分離する。
  • 公開ヘッダーから上位層のヘッダーをincludeしない。
  • 入力は不変Viewまたは値、出力はResultと診断一覧にする。
  • 例外を契約にせず、エラー分類を戻り値で表現する。
  • 公開型は「変更理由が同じデータ」だけを束ねる。

DLL境界で追加する制約

  • 原則としてC ABIを使用し、opaque handleで状態を隠す。
  • Siv3D::String、Array、STLコンテナ、例外、RTTI型を公開しない。
  • uint32_t 等の固定幅型、UTF-8バイト列、明示サイズを使う。
  • 構造体に struct_size と予約領域を持たせる。
  • 生成・破棄関数を対にし、確保側モジュールで解放する。
  • API version、ABI version、build identityを取得可能にする。
  • Debug/ReleaseやRuntime Libraryの混在を前提にしない。

契約に必ず記録する項目

項目記録内容
責務何を保証し、何を担当しないか。
入力有効範囲、文字コード、単位、null可否、順序、最大サイズ。
出力所有権、寿命、決定性、順序保証、部分結果の有無。
失敗エラーコード、再試行可否、状態変更の有無、診断取得方法。
並行性thread-safeか、handle単位か、呼出しスレッド制約。
互換性SemVer方針、破壊的変更の条件、旧版サポート期間。
検証証拠ソースrevision、公開契約hash、テスト結果、ツールチェーン。

6. 将来APIと未実装機能の窓口

将来性は「未実装関数を大量に並べること」ではなく、機能を安全に発見し、対応版だけを取得できる拡張機構で確保する。

推奨する最小Gateway

概念上の公開機能:
- lt3_get_api_version()          : API/ABIバージョンを返す
- lt3_get_build_identity()       : ビルド識別子と契約ハッシュを返す
- lt3_query_capability(id)       : Unsupported / Planned / Experimental / Stable
- lt3_get_extension(id, version) : 対応時だけversioned function tableを返す
- lt3_get_last_diagnostic(...)   : 呼出し単位の構造化診断を取得する

共通結果:
Ok / InvalidArgument / Unsupported / NotImplemented /
VersionMismatch / InvalidState / BufferTooSmall / InternalError

未実装呼出しの保証

  • NotImplemented または Unsupported を明示的に返す。
  • 成功値・空の成功結果へ偽装しない。
  • 外部から観測可能な状態を変更しない。
  • 機能ID、API版、呼出し元文脈を構造化診断へ残す。
  • 同一警告を「機能ID × セッション」単位で抑制し、毎フレーム出力しない。

公開しない将来仕様

  • 引数・所有権・失敗条件が未確定の具体的関数。
  • UIやScene構造を前提にした拡張。
  • 内部のBattleWorldやDefinitionStoresを直接返すAPI。
  • 呼出し順序だけで成立する暗黙プロトコル。

Planned は「存在予約」であり呼出し可能を意味しない。Experimental は互換性保証範囲を別namespace/extension IDで隔離し、Stableへ昇格するまで通常の互換保証対象から外す。

7. 段階導入ロードマップ

期間ではなく品質ゲートで進行する。各フェーズは独立した変更として完了させ、次のフェーズを同一PRへ混在させない。

Phase 0

基準線と変更台帳

目的: 「速くなった」「確認不要」の判断を感覚ではなく比較可能にする。

成果物

  • Debug/Releaseのclean・incremental build時間。
  • 主要起動経路のスモーク手順: title、通常battle、--mod、--quick-battle。
  • モジュール台帳: owner、責務、依存、公開契約、source hash、再確認条件。
  • 現行挙動のcharacterization test候補一覧。

変更制約

  • ゲーム挙動を変更しない。
  • 推測の環境削減量を記載しない。
  • 計測コマンドと環境を再現可能に記録する。

進む条件: 基準値、スモーク経路、台帳形式、再確認トリガーがレビュー済み。

停止条件: clean buildまたは主要起動経路が既に不安定。先に既存不具合を分類する。

Phase 1

契約・テスト・依存ルールの基盤

目的: ファイル配置ではなく、機械的に守れる境界を作る。

  • 最小のテスト用プロジェクトまたはテスト実行可能ファイルを追加する。
  • Result、Diagnostic、Capability、Versionの共通契約を設計する。
  • 禁止includeルールと依存方向を文書化し、可能ならCIで検査する。
  • App/Scene/UIをHostと定義し、Coreからの参照を禁止する。
  • 既存APIを変えず、Adapterを挟めるseamを追加する。

進む条件: 空の境界プロジェクトが全構成でbuildでき、最低1本の契約テストと禁止依存検査が動作する。

停止条件: テスト導入が本体起動やSiv3Dリンクへ不要な依存を持ち込む。

Phase 2

Pathfindingを分離パイロットにする

目的: 小さく決定的な機能で、抽出手順と検証方法を実証する。

  • PathMapSnapshot、整数座標、経路結果をSiv3D非依存の型へ置換または変換する。
  • A*・近傍探索をPure Coreへ、BattleWorld snapshotとQuarterView座標変換をHost Adapterへ分離する。
  • 到達可否、境界、予約セル、同一点、決定的tie-break、空mapをテストする。
  • 旧実装とのgolden comparisonを固定seed/fixtureで行う。

進む条件: 既存の経路結果と許容差内で一致し、Core公開ヘッダーがSiv3D・UI・BattleWorldをincludeしない。

停止条件: hot pathで測定可能な退行、または座標変換の責務が曖昧なまま。

Phase 3

Mod / Content PathをPolicyとI/Oへ分離

目的: Modの安全性・継承規則・ID規則を単一の契約にする。

  • case-insensitive ASCII stable IDの正規化と検証をPure Policyへ移す。
  • 1 Modのみ有効、mod.toml の明示継承、scenario/skirmish、--quick-battle の規則を契約化する。
  • filesystem canonical化、symlink、Warehouse探索をI/O Adapterに閉じ込める。
  • 実ファイルが未作成の将来パスと既存パスの安全性を別APIとして区別する。
  • プロジェクト登録だけで欠落判定せず、実ファイル、Git追跡、ignore、runtime解決を診断対象に含める。

進む条件: traversal、絶対パス、重複ID、大小文字、継承有無、symlink逸脱のテストが通り、既存Modが読める。

停止条件: security checkを弱める互換回避が必要になる。仕様を先に明文化する。

Phase 4

TOML永続化とDefinition検証を分離

目的: TOML I/O、schema変換、参照整合性、ゲーム内Storeを別々に確認可能にする。

  • Skill、Unit、Resource、BuildAction、AI Profileのparse結果と診断を共通形式へ寄せる。
  • 参照整合性検証をファイルI/Oなしで実行可能にする。
  • 保存は全文を先に構築し、行ごとの自動改行追加を使わず、必要最小限の改行だけを明示する。
  • temporary → backup → replace → recoveryの失敗点をテストする。
  • 未知キー、schema version、重複tag、未解決参照の方針を契約化する。

進む条件: 既定ゲームと代表Modの読込結果が同等で、保存golden fileと失敗復旧テストが通る。

停止条件: Parser都合の型がDomain全体へ漏れる、または保存結果が不要な改行差分を生む。

Phase 5

Simulation CoreをFacadeで囲う

目的: BattleWorld内部を直接操作せず、コマンド入力とスナップショット出力で戦闘を扱う。

  • AudioAssetCache* と ModContext* をBattleWorldから除き、音声要求EventをHostへ返す。
  • 初期化、tick、order、query、snapshot、event drainのFacadeを定義する。
  • UI/Editor用の直接可変アクセスはApplication Adapterに限定し、移行期間を明示する。
  • 固定seed、固定delta、同一Command列で決定性を検証する。
  • BattleWorld invariant検査をテストとDebug診断へ組み込む。

進む条件: title/通常battle/mod/quick-battleの統合スモークが通り、主要戦闘fixtureのsnapshotが同等。

停止条件: FacadeがBattleWorld全体を返す、UI型を受ける、または1フレームごとに大量コピーする。

Phase 6

限定的なDLL Gatewayを評価・導入

目的: 独立配布、外部ツール共有、差し替えなど、DLL固有の利益がある境界だけをバイナリ化する。

  • 候補ごとに「静的ライブラリでは達成できない要求」を記録する。
  • C ABI、opaque handle、versioned function table、capability queryを実装する。
  • ABI互換テスト、旧DLLロード、version mismatch、欠落DLL、未実装APIをテストする。
  • DLL配置、署名/hash、探索順、ロード失敗時のユーザー向け診断を定義する。
  • 未実装呼出しは明示エラー、無変更、抑制ログを保証する。

進む条件: DLL化の便益が測定で確認でき、静的版と同じ契約suiteを通過し、HostがABI内部型へ依存しない。

停止条件: 目的が「AIに読ませないためだけ」、またはSiv3D/STL/BattleWorldをABIへ露出する必要がある。

Phase 7

変更影響ベースの限定チェック運用

目的: 省略可能範囲を自動判定し、必要時だけ深い確認へ昇格する。

  • モジュールごとにsource hash、public contract hash、dependency lock、test evidenceを保存する。
  • 変更ファイルから依存グラフを辿り、対象テストとレビュー範囲を選ぶ。
  • 公開契約、toolchain、runtime、共有schema変更時は全体確認へ昇格する。
  • 定期的な全体確認はカレンダー固定だけでなく、リスクと変更量をトリガーにする。
  • 省略理由を機械可読な台帳とレビュー結果へ残す。

完了条件: 限定チェックと全体チェックの結果差を一定期間監視し、見逃しがないこと、時間削減が再現することを確認する。

停止条件: 依存グラフ外の暗黙参照、生成物不一致、限定チェックでのみ再現する見逃しが発生する。

8. チェック戦略と再確認トリガー

検証ピラミッド

契約テスト

全モジュールで常時実行。入力、出力、失敗、所有権、version、capabilityを検証する。

統合スモーク

Hostとの接続変更時に、title、battle、mod、quick-battle、主要Editor起動を確認する。

全体回帰

公開契約、toolchain、Siv3D、schema、共有状態、DLL loader変更時に実行する。

変更時チェック行列

変更必須チェック内部再調査全体確認
実装のみ、公開契約hash不変対象単体・契約・直接依存変更モジュールのみ原則不要
